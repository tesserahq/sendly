# 0002 — Broadcast Sending

## Problem Statement

Sendly today only sends one email to one recipient at a time. Several external apps need to send the same newsletter-style content to a list of recipients — with light personalization (first name, etc.) — and there's no way to do that through Sendly without the caller looping over `/emails` themselves, losing batch-level tracking, and having no way to know when someone unsubscribes.

There's also no unsubscribe handling at all today: Postmark's `SubscriptionChange` webhook event isn't even mapped to a status, so an unsubscribe currently gets silently dropped into an "unknown" event type with no downstream effect. Callers have no way to find out that a recipient opted out, and nothing stops Sendly from emailing that person again on the next send.

## Solution

Add a new `POST /broadcasts/send` endpoint that accepts a list of structured recipients (email required, name/attributes optional) plus the same content options `/emails/send` already supports (inline `html`/`text`, or `template_id`/`template_alias` + `template_variables`). Each recipient gets their own `Email` row, grouped by a server-generated UUID `batch_id`; callers use free-form `tags` and `metadata` for their own campaign identifiers and other custom information.

Sends happen through Postmark's Broadcast message stream (a single, globally-configured stream ID) rather than the default transactional stream, so Postmark manages the unsubscribe link/header itself. The request itself only does cheap, O(1)-round-trip work: one batched suppression lookup against the whole recipient list, and one durable write of the raw (unrendered) recipient data and content options — nothing in the request loops per recipient doing template rendering or per-row inserts, so acceptance time doesn't grow with list size and the endpoint can still return `{batch_id, queued_count, suppressed_count}` immediately. Everything per-recipient after that is chunked and asynchronous, in two stages: a **prepare** stage renders each non-suppressed recipient's content and writes their `Email` row, immutable delivery payload, and outbox entry; a **send** stage (the existing outbox pipeline) groups pending outbox entries into fixed-size chunks and hands each chunk to a Celery task that sends it via Postmark's Bulk API (`POST /email/batch`) in a single HTTP call. Both stages are the first real workload for the currently-empty `app/tasks/`. Chunking the send step this way keeps large sends from making one HTTP round-trip per recipient, which matters both for wall-clock throughput and for staying under Postmark's per-second API rate limit; chunking the prepare step the same way is what keeps rendering and row creation off the request path entirely.

When Postmark posts an authenticated recipient-unsubscribe `SubscriptionChange` webhook back, Sendly records the recipient in a new suppression table (scoped per project) and publishes an `email.unsubscribed` NATS event via the existing `tessera_sdk.infra.events` publisher, carrying the email's tags/metadata so downstream consumers know which campaign/list the person opted out of. Future broadcasts automatically skip suppressed recipients, even if the caller's list still includes them.

## User Stories

1. As a Sendly consumer, I want to send one piece of content to a list of recipients in a single API call, so that I don't have to loop over the single-send endpoint myself.
2. As a Sendly consumer, I want to provide recipients as structured objects (email, first name, last name, arbitrary attributes) rather than a flat list of email strings, so that I can personalize content per recipient.
3. As a Sendly consumer, I want first name/last name/attributes to be optional per recipient, so that I can send to lists where I only have email addresses.
4. As a Sendly consumer, I want per-recipient attributes merged into that recipient's template variables, so that `${first_name}` (etc.) renders correctly in each recipient's copy of the email.
5. As a Sendly consumer, I want to reuse the same `html`/`text`/`template_id`/`template_alias`/`template_variables`/`subject`/`from_email`/`custom_headers`/`idempotency_key`/`attachments` fields that `/emails/send` already supports, so that I don't have to learn a second content model.
6. As a Sendly consumer, I do not want to specify `cc`/`bcc` on a broadcast send, since it has no coherent per-recipient meaning for a fan-out send.
7. As a Sendly consumer, I want Sendly to always generate a `batch_id` for each broadcast, so that every send has an unambiguous query key without callers coordinating identifiers.
8. As a Sendly consumer, I want to attach my own campaign identifiers and other custom information through `tags` and `metadata`, so that I can correlate broadcasts with my own systems without overloading `batch_id`.
9. As a Sendly consumer, I want to attach `tags` and `metadata` to a broadcast send, so that I can filter/query emails by campaign-relevant data later.
10. As a Sendly consumer, I want `tags` and `metadata` to also be usable on the existing single-recipient `/emails/send` endpoint, so that filtering is consistent regardless of which endpoint sent the email.
11. As a Sendly consumer, I do not want `batch_id` to be settable on `/emails/send`, since that concept only makes sense for a multi-recipient send.
12. As a Sendly consumer, I want the broadcast endpoint to return immediately with a `batch_id` and recipient counts, so that a large recipient list doesn't force me to hold open a long HTTP request.
13. As a Sendly consumer, I want each recipient's email to still be sent through Sendly's normal per-email status tracking (`queued` → `sent`/`failed`/etc.), so that I can query individual delivery status the same way I do today.
14. As a Sendly consumer, I want a recipient who has previously unsubscribed to be automatically skipped on future broadcast sends, even if my own list still includes them, so that I don't accidentally re-email someone who opted out.
15. As a Sendly consumer, I want the response from a broadcast send to tell me how many recipients were skipped as already-suppressed, so that I can reconcile counts against my own list size.
16. As a Sendly consumer, I want broadcast emails sent through Postmark's Broadcast message stream (not the transactional stream), so that Postmark's own unsubscribe handling and sending reputation separation applies.
17. As a Sendly consumer, I want Postmark's unsubscribe webhook (`SubscriptionChange`) to be correctly recognized and mapped to an `unsubscribed` status, instead of silently falling into an unmapped/unknown event type.
18. As a Sendly consumer, I want Sendly to publish a NATS event when a recipient unsubscribes, so that my own systems can react (e.g. remove them from my source-of-truth list) without polling Sendly.
19. As a Sendly consumer, I want the unsubscribe NATS event to include the email's tags/metadata, so that I know which campaign/batch the person unsubscribed from without a follow-up lookup.
20. As a developer extending Sendly, I want the unsubscribe NATS event to follow the same `Event`/`event_type`/`event_source` CloudEvents convention already used by other TesseraHQ services (via `tessera_sdk.infra.events`), so that downstream consumers can rely on a consistent shape across services.
21. As a developer extending Sendly, I want the template-resolution/Mako-rendering logic shared between the single-send and broadcast-send paths, so that template behavior (variable interpolation, layout wrapping, error handling) doesn't diverge between the two.
22. As a developer extending Sendly, I want each recipient's status and provider result handled independently within a chunk task, so that a per-recipient validation failure does not block or fail other recipients; transport failures may retry the chunk as documented.
23. As an operator, I want the Postmark broadcast message stream ID configured once globally (like `postmark_api_key` today), so that broadcast sending doesn't require new per-tenant provider configuration ahead of anything else needing it.
24. As a Sendly consumer retrying a timed-out broadcast request, I want the same idempotency key to return the original batch result without sending recipients twice.
25. As a Sendly consumer, I want to query a broadcast by `batch_id` and filter sent email by tags, so campaign tracking is usable rather than merely stored.
26. As a Sendly consumer sending to a large recipient list, I want Sendly to send via Postmark's Bulk API instead of one HTTP call per recipient, so that a broadcast of thousands of recipients doesn't take thousands of round-trips or risk hitting Postmark's API rate limit.
27. As an operator, I want the number of recipients grouped into each Bulk API call to be configurable, so that I can tune the throughput/parallelism/blast-radius trade-off without a code change.
28. As a Sendly consumer sending to a large recipient list, I want template rendering and row creation to happen in the background rather than inside the request, so that accepting a broadcast doesn't itself risk timing out for a large enough list — the same problem chunked sending already solves for the provider call shouldn't reappear one step earlier in the pipeline.

## Implementation Decisions

- **New endpoint**: `POST /broadcasts/send`, its own router (`app/routers/broadcast.py`), RBAC resource `"broadcast"` (via the existing `build_rbac_dependencies` pattern), separate from `/emails/send`. Existing `/emails/send` behavior is unchanged except for accepting optional `tags` and `metadata`.
- **Request schema** (`app/schemas/broadcast.py`, `BroadcastCreateRequest`): `project_id`, `from_email`, `subject`, `html`, `text`, `attachments`, `template_id`, `template_alias`, `template_variables` (base/shared variables merged with each recipient's own), `custom_headers`, `idempotency_key`, `tags: List[str]`, `metadata: Dict[str, Any]`, and `recipients: List[BroadcastRecipient]` where `BroadcastRecipient` = `{email: EmailStr, first_name: Optional[str], last_name: Optional[str], attributes: Dict[str, Any] = {}}`. `batch_id`, `priority`, `cc`, and `bcc` are not accepted; Sendly generates the batch UUID and callers use tags/metadata for their own correlation data.
- **Schema changes on `Email`**: add `batch_id` (nullable string, indexed), `tags` (nullable JSON array of strings), `metadata` (nullable JSON object). `tags`/`metadata` are also accepted on `EmailCreateRequest`/`/emails/send`; `batch_id` is broadcast-only and never caller-settable. Add an immutable `email_delivery_payloads` table keyed by `email_id`, containing the fully resolved `from_email`, `to`, `subject`, HTML/text bodies, attachments, custom headers, and message stream required for delivery. The task must never re-fetch a template or depend on request-only recipient attributes.
- **Batch, recipients, and outbox tables**: add `broadcast_batches` (`id`, `project_id`, `batch_id`, `idempotency_key`, `request_fingerprint`, `content_spec` — the shared, not-yet-rendered content options: `html`/`text`/`template_id`/`template_alias`/`template_variables`/`subject`/`from_email`/`custom_headers`/`attachments`/`tags`/`metadata` — plus `queued_count`, `suppressed_count`), with unique `(project_id, batch_id)` and unique `(project_id, idempotency_key)` when the key is non-null; `broadcast_recipients` (`id`, `batch_id`, `email`, `first_name`, `last_name`, `attributes` JSON, `suppressed` bool, `prepared` bool) holding the raw per-recipient data the prepare stage consumes; and `email_send_outbox` keyed by `email_id` (unchanged). `batch_id` is generated server-side as a UUID. The batch row is the durable idempotency authority: a repeat key with the same fingerprint returns the original result; the same key with different content returns `409 Conflict`.
- **New table**: `email_suppressions` (`project_id`, `email`, `unsubscribed_at`, `source`), unique on `(project_id, email)`. New `SuppressionRepository` with `is_suppressed(project_id, email)`, `is_suppressed_bulk(project_id, emails) -> Set[str]` (one query, not N), `create_or_update_suppression(...)`, and `remove_suppression(project_id, email)`.
- **`SendBroadcastCommand`** (`app/commands/send_broadcast_command.py`): resolves the idempotency key first. Runs exactly one query — `SuppressionRepository.is_suppressed_bulk` — against the full recipient list to compute `queued_count`/`suppressed_count`; does **not** render any content and does **not** create `Email` rows. In one database transaction it creates the `broadcast_batches` row (with `content_spec` and the computed counts) and bulk-inserts one `broadcast_recipients` row per submitted recipient (`suppressed` set from the lookup, `prepared=false`). It returns `{batch_id, queued_count, suppressed_count}` immediately; dispatch of the prepare stage happens separately, after commit, via the prepare publisher.
- **`EmailRenderingService`** (new, `app/services/email_rendering_service.py`): extracted from `SendEmailCommand`'s `_resolve_template`/`_resolve_inline`/`_render`/`_fetch_template`/`_to_namespace`. Given template reference or inline html plus merged variables, it returns the fully resolved delivery content. `SendEmailCommand` is refactored to depend on it, so single-send and broadcast rendering behavior cannot drift.
- **Prepare publisher** (`app/services/broadcast_prepare_publisher.py`): same two-trigger shape as the outbox publisher, one stage earlier. (1) Fast path: `SendBroadcastCommand` calls it directly, synchronously, immediately after its transaction commits — it reads that batch's non-suppressed, unprepared `broadcast_recipients` rows, groups them into chunks of `broadcast_chunk_size`, and dispatches one Celery task per chunk (each carrying its list of `broadcast_recipients` ids) before the HTTP request returns. (2) Recovery path: a periodic Celery-beat sweep over unprepared rows older than a short grace period, across all batches, as a crash-recovery backstop — not the normal dispatch path.
- **`prepare_broadcast_chunk_task`** (new Celery task, `app/tasks/`): given a `batch_id` and a list of `broadcast_recipients` ids, loads the batch's `content_spec`, rechecks suppression for the chunk (a recipient suppressed between acceptance and this task still gets skipped — no `Email` row is created for them, and their `broadcast_recipients` row is marked `prepared=true` without one), and for each remaining recipient merges its `first_name`/`last_name`/`attributes` into `content_spec.template_variables` and calls `EmailRenderingService`. In one transaction per chunk it creates each recipient's `Email` row (`status=queued`, `batch_id`/`tags`/`metadata` from `content_spec`), immutable delivery payload, and outbox entry, and marks the corresponding `broadcast_recipients` rows `prepared=true`. This is what the "prepare" stage means: rendering and per-recipient row creation happen here, in the background, chunked exactly like sending is — never inside the original request.
- **Outbox publisher** (`app/services/broadcast_outbox_publisher.py`): unchanged in shape from the prepare publisher, one stage later. (1) Fast path: `prepare_broadcast_chunk_task` calls it directly, synchronously, after its own transaction commits — it reads that chunk's just-created pending outbox entries, groups them into chunks of `broadcast_chunk_size` (config, default 100, hard-capped at Postmark's batch max of 500), and dispatches one Celery task per chunk (each carrying its list of `email_id`s). (2) Recovery path: a periodic Celery-beat job (e.g. every 60s) runs the same publisher over *all* still-pending outbox entries older than a short grace period — a backstop, not how normal broadcasts get dispatched. A chunk boundary never spans more than one broadcast batch but may be smaller than `broadcast_chunk_size` on the tail of a batch or a prepare chunk.
- **`send_broadcast_chunk_task`** (new Celery task, `app/tasks/`, replaces the earlier per-recipient `send_broadcast_email_task`): given a list of `email_id`s, loads each one's immutable delivery payload, rechecks suppression for the whole chunk immediately before assembling the request, and calls `EmailLifecycleService.record_send_suppressed()` for any recipient suppressed since acceptance. This writes the terminal `suppressed` status and event without treating an opt-out as a provider failure. The task sends the remaining payloads in one `POST /email/batch` call via `PostmarkProvider.send_batch`. Postmark's batch endpoint returns a 200-level response containing a per-message `ErrorCode`/`MessageID` result even when individual messages fail validation; the task walks that array and records each recipient's outcome individually via `EmailLifecycleService`, exactly as the single-send path does. If the HTTP call itself fails at the transport level (timeout, connection error, Postmark 5xx — as opposed to a per-message validation error), the whole chunk is retried as a unit; this accepts a small risk of double-sending a recipient whose message was actually processed by Postmark before the connection dropped, since the batch endpoint has no per-message idempotency key to check against before retrying (see Further Notes).
- **Email lifecycle changes**: add terminal `EmailStatus.SUPPRESSED` and `EmailLifecycleService.record_send_suppressed(email, reason, suppressed_at)`, which sets that status and creates a `suppressed` email event. Suppressed recipients are distinct from provider failures in email queries and batch counts.
- **Postmark provider changes** (`app/providers/postmark_provider.py`): add `send_batch(requests: List[EmailCreateRequest]) -> List[EmailSendResult]`, implemented via `postmarker`'s `client.emails.send_batch(*emails, MessageStream=...)`, alongside the existing single-message `send_email`. Both send the entire persisted payload, including `MessageStream=<configured broadcast stream id>` for broadcasts and the existing transactional default for `/emails/send`. Implement Postmark-supported headers, attachments, and text body rather than only accepting them in the API schema. Normalize `SubscriptionChange` using `Recipient`, `ChangedAt`, `SuppressSending`, `Origin`, `SuppressionReason`, `MessageStream`, and nullable `MessageID`; it is not a blanket `subscriptionchange → unsubscribed` mapping.
- **Config and webhook authentication**: add global `postmark_broadcast_stream_id` and `broadcast_chunk_size` (default 100). Webhook authentication is already handled at the route level, not inside `PostmarkProvider`: Postmark's webhook is configured to call `POST /providers/{provider_id}/delivery-events` with an Identies-issued API key, which the existing `rbac_provider_delivery_events["create"]` dependency (the same `authorize()`/`tessera_sdk` mechanism every other Sendly endpoint uses) validates before the request reaches `ProcessDeliveryEventsCommand`. This is the real authentication boundary for inbound Postmark events, including `SubscriptionChange`. `PostmarkProvider.verify_webhook()` remains a stub (`return True`) — it is not the auth mechanism in use and is not being changed as part of this PRD.
- **Unsubscribe write path** (new `HandleSubscriptionChangeCommand`, `app/commands/providers/handle_subscription_change_command.py`): `ProcessDeliveryEventsCommand` stays the single entry point for provider webhooks and keeps calling `EmailLifecycleService.record_webhook_event` for every event as it does today, but for `event_type == "unsubscribed"` (and reactivation) it additionally delegates to `HandleSubscriptionChangeCommand`, invoked after the lifecycle write. This keeps `EmailLifecycleService` scoped to its documented single responsibility (`Email.status`/`EmailEvent` writes only) — suppression-table writes and NATS publishing are a separate command's job, not bolted onto the lifecycle service or left unowned in the webhook route. `HandleSubscriptionChangeCommand.execute(email, raw_payload)`: when `SuppressSending=true`, uses the message's `Email.project_id` to upsert the project-scoped suppression via `SuppressionRepository` and, only for a recipient-originated unsubscribe, publishes `email.unsubscribed` via `build_email_unsubscribed_event`/`NatsEventPublisher`. When `SuppressSending=false`, removes the matching project suppression via `SuppressionRepository.remove_suppression` rather than publishing an unsubscribe. A null-`MessageID` subscription event cannot be safely assigned to a project with the global stream; the command records it for operations (structured log, no exception raised back to `ProcessDeliveryEventsCommand`) and does not mutate a project suppression until a project ownership model exists.
- **NATS event** (`app/events/email_events.py`, new): `EMAIL_UNSUBSCRIBED = "email.unsubscribed"`; `build_email_unsubscribed_event(email)` returns a `tessera_sdk.infra.events.Event` with `event_type=event_type(EMAIL_UNSUBSCRIBED)`, `source=event_source(f"/emails/{email.id}")`, `subject=f"/emails/{email.id}"`, `event_data` containing the email's id/project_id/to_email/batch_id/tags/metadata, `labels`/`tags` carrying `project_id`/`batch_id` — following the same shape as `custos`'s `role_events.py` and `looply`'s `contact_list_events.py`. Published via `tessera_sdk.infra.events.NatsEventPublisher().publish_sync(...)`, matching `looply`'s `UnsubscribeUserCommand`.
- **Task granularity**: one Celery task per chunk of up to `broadcast_chunk_size` recipients, for *both* stages — `prepare_broadcast_chunk_task` (render + row creation) and `send_broadcast_chunk_task` (Postmark Bulk API call). `Email` rows, delivery payloads, and outbox entries remain one-per-recipient (unchanged) once created — only the dispatch, rendering, and provider-call steps are chunk-shaped, keeping per-recipient status tracking and per-recipient retry semantics intact while keeping both request-acceptance and send throughput independent of list size.
- **Query contract**: extend `GET /emails` with `batch_id` and exact `tag` filters, always scoped by `project_id`; include `batch_id`, `tags`, and `metadata` in email response schemas. Add `GET /broadcasts/{batch_id}` for the batch's accept-time counts (`queued_count`/`suppressed_count`, fixed at acceptance) plus live processing state (`prepared_count`: `broadcast_recipients` rows with `prepared=true`), scoped to its project — since `Email` rows for a batch may not all exist yet immediately after acceptance, `prepared_count` is how a caller can tell whether the prepare stage has caught up before querying individual `Email` statuses.

## Testing Decisions

- Good tests here assert observable behavior (rows created, status transitions, events published, NATS payload shape) — not internal call sequencing.
- `EmailRenderingService`: unit-tested in isolation (no DB, no provider) covering template resolution, layout wrapping, variable interpolation, and error cases — same coverage `SendEmailCommand`'s rendering currently gets, just against the extracted module.
- `SendBroadcastCommand`: integration-tested for an atomic batch/`broadcast_recipients` write, server-generated `batch_id`, correct `suppressed`/`queued` counts from a single bulk suppression lookup, and idempotency (same key/same request returns the original result; same key/different request returns `409`; no duplicate recipient rows). Also assert it does **not** create any `Email` rows and does **not** call `EmailRenderingService` — that work belongs to the prepare stage, and a regression that moves it back into the command should fail this test, not just be caught by eyeballing latency later.
- Prepare publisher: unit-tested directly (no Celery, no HTTP) for chunk grouping and both triggers separately — `SendBroadcastCommand` invokes it synchronously post-commit with exactly that batch's unprepared, non-suppressed recipients, and the periodic sweep picks up rows left unprepared past the grace period across batches without re-dispatching rows already claimed.
- `prepare_broadcast_chunk_task`: use Celery eager mode. Assert it merges each recipient's `first_name`/`last_name`/`attributes` into the batch's shared `template_variables` before rendering, creates exactly one `Email`/payload/outbox row per non-suppressed recipient in the chunk, skips row creation (but still marks `prepared=true`) for a recipient suppressed since acceptance, and that a template-rendering error for one recipient doesn't prevent the rest of the chunk from being prepared.
- Outbox publisher: unit-tested directly (no Celery, no HTTP) for chunk grouping (chunk sizes respect `broadcast_chunk_size`, the tail chunk of a batch is smaller than the configured size rather than dropped or merged into the next batch) and for both triggers separately — that `prepare_broadcast_chunk_task` invokes it synchronously post-commit with exactly that chunk's pending entries, and that the periodic sweep picks up entries left pending past the grace period regardless of which batch they belong to, without re-dispatching entries a chunk task has already claimed.
- `send_broadcast_chunk_task`: use Celery eager mode. Assert the task sends the immutable payloads rather than consulting templates, that a suppression written after acceptance prevents that recipient's message from being included in the batch call and records `suppressed` rather than `failed`, and that a per-message `ErrorCode` in the batch response is recorded as that specific recipient's failure without affecting the other recipients in the same chunk.
- A timing test asserting `SendBroadcastCommand.execute()`'s wall-clock cost does not scale with recipient count (e.g. 10 recipients vs. 5,000 recipients complete in comparable time) — this is the concrete regression test for the problem this whole prepare/send split exists to fix.
- Postmark provider: test all persisted fields are mapped to Postmark for both `send_email` and `send_batch`, broadcast sends pass the configured `MessageStream` in both paths, `send_batch` correctly maps a mixed-outcome batch response (some `ErrorCode` 0, some non-zero) back to per-message results in request order, and subscription changes preserve `Recipient`, `ChangedAt`, `SuppressSending`, origin, reason, stream, and nullable `MessageID`.
- `HandleSubscriptionChangeCommand`: unit-tested with a mocked `SuppressionRepository`/`NatsEventPublisher` (no DB, no NATS) covering recipient unsubscribe (suppression upserted + NATS published), reactivation (suppression removed, no unsubscribe event), non-recipient suppressions, and null-`MessageID` events (no cross-project mutation, operational log only, no exception propagated).
- Unsubscribe flow (integration): `ProcessDeliveryEventsCommand` invokes `HandleSubscriptionChangeCommand` for `unsubscribed` events and not for other event types; end-to-end coverage that a `SubscriptionChange` webhook payload results in both the `EmailEvent`/status write (via `EmailLifecycleService`) and the suppression row. The delivery-events route's existing RBAC test coverage (a request without a valid Identies API key is rejected) is sufficient for the auth boundary — no separate webhook-specific auth test is needed since it reuses the standard `authorize()` dependency.
- Router tests: verify `POST /broadcasts/send` RBAC and idempotency behavior, and verify `GET /emails` tag/batch filters plus `GET /broadcasts/{batch_id}` (including `prepared_count`) are project scoped.

## Out of Scope

- Persistent audiences/subscriber lists — the caller's list is the source of truth on every call; Sendly stores no membership beyond the suppression table.
- A Sendly-hosted unsubscribe link/token/endpoint — Postmark's Broadcast stream hosts the unsubscribe mechanism.
- Per-project/tenant Postmark broadcast stream configuration.
- `cc`/`bcc` on broadcast sends.
- Per-project/tenant `broadcast_chunk_size` tuning — one global config value for now, matching the global broadcast stream ID.
- Reconciling exactly which messages in a chunk actually sent before a transport-level failure — the design accepts whole-chunk retry and its small double-send risk instead (see Further Notes).
- A real-Redis-broker test environment — tests run Celery in eager mode.
- Recipient list size limits/rate limiting — not addressed in this PRD; flagged as a follow-up if large lists prove to be a problem in practice.
- Any change to the existing `/emails/send` request contract beyond adding optional `tags`/`metadata`.

## Further Notes

- `looply` (a sibling TesseraHQ service) already implements contact-list subscribe/unsubscribe with its own `ContactList`/`Contact`/`ContactListMember` models and NATS event publishing. It's worth being aware this exists as prior art for a full persistent-audience model — if Sendly's needs grow beyond "send to a list I already have," integrating with or delegating to `looply` may be worth revisiting rather than growing a second subscriber-management system inside Sendly. For this PRD's stateless scope, that's not needed.
- `app/tasks/` currently contains zero tasks despite Celery/Redis being wired dependencies; this PRD is what puts real code there for the first time, which also means worker deployment (making sure a Celery worker process actually runs in every environment) becomes a real operational requirement, not just a library dependency.
- **Accepted risk — chunk-retry double-send**: Postmark's `POST /email/batch` endpoint has no per-message idempotency key, so if a chunk's HTTP call fails at the transport level after Postmark has already processed some of the messages in it, retrying the whole chunk can double-send those. This is treated as an already-accepted class of risk (the design makes the same trade-off for individual sends elsewhere) rather than solved outright, since solving it fully would require inventing custom per-message dispatch tracking that Postmark's API doesn't support querying. Keeping `broadcast_chunk_size` small (default 100, not Postmark's 500 max) bounds how many recipients any single occurrence of this can affect.
- Postmark bills per email sent regardless of whether it's sent via the single-send or batch endpoint — switching to the Bulk API is a throughput/rate-limit optimization, not a cost optimization.
- **Prepare/send symmetry**: rendering and row creation used to happen synchronously inside `SendBroadcastCommand`, which meant the same request-timeout risk the send stage was built to avoid (one HTTP call per recipient) reappeared one step earlier (one template render + DB insert per recipient, still inside the request). Splitting rendering into its own chunked, asynchronous "prepare" stage — structurally identical to the existing "send" stage, just one step earlier in the pipeline — fixes this without changing the response contract: the only synchronous per-recipient-list work left in the request path is one bulk suppression query and one bulk insert of raw (unrendered) recipient rows, both O(1) round-trips regardless of list size. The residual cost of that bulk insert still technically grows with list size, but inserting plain rows is much cheaper than the same count of Mako renders plus three related-table inserts each — a recipient-count cap remains explicitly out of scope (see Out of Scope) as a separate, lower-priority concern rather than something this split was required to also solve.
